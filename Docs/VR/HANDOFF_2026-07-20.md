## Root causes found (all fixed in `87d3b5aa`)

1. **Trigger didn't fire.** `Pawn.bFire`/`bAltFire`/`bDuck` are *byte*
   properties (`UActor.h`: `uint8_t& bFire()` etc. — confirmed directly
   against the header, not assumed), not bool. `UObject::SetBool()`
   (`UObject.cpp:311`) unconditionally `static_cast`s the resolved
   `UProperty*` to `UBoolProperty*` and does 32-bit bitfield math on it —
   calling it on a byte property is undefined behavior (reads/writes
   memory belonging to neighboring properties, not the one bit you
   wanted). This is a **generic engine bug**, not VR-specific — the exact
   same call shape (`viewport->Actor()->SetBool(name, true)`) is what
   `Engine::UpdateInput()` uses for every keyboard/mouse `Button`
   binding too, so keyboard/mouse fire is potentially subject to the same
   bug. Worth a standalone investigation later (see "Also worth
   investigating" below) — today's fix only touches the VR controller
   path (writes through the native byte accessors directly, bypassing
   `SetBool` entirely for these three properties).
2. **Movement extremely slow.** Wrong scale assumption — I'd treated
   `aBaseY`/`aStrafe`/`aUp` as if they expected literal UU/sec. Tracing
   `Engine::InputCommand`'s `Axis` branch shows the real convention: a
   held key produces `activeInputAxes[name] = Speed * delta`, where a
   press-generated `delta` is a fixed `20` (`InputEvent()`,
   `Engine.cpp`) and a typical default keybind is `Axis aBaseY
   Speed=350` — i.e. a full press feeds ~7000, not something UU/sec-sized.
   Fixed `MOVE_SCALE` to `7000.0f` to match (documented in-code).
3. **Looking direction didn't affect running direction; weapon invisible.**
   `Pawn.Rotation` (what movement axes and the first-person weapon
   viewmodel are positioned relative to) was only ever nudged by the
   one-time recenter capture — nothing kept it synced to the player's
   *live* head yaw as they looked around. Fixed by capturing the live
   head yaw once per XR frame into a new `Engine::xrHeadYawUE` member
   (`Engine.cpp`'s `Run()` XR frame loop, right where the per-eye render
   pose is composed) and applying it to `Pawn.Rotation.Yaw` every
   controller-input tick (`UpdateVRControllerInput()`) — Pitch/Roll
   untouched, so looking up/down doesn't tilt the collision cylinder.
   Right-stick-X turning was changed to increment `xrYawOffsetUE`
   (the recenter offset) instead of driving a separate `aTurn` axis,
   since driving `aTurn` would just get overwritten by this same yaw sync
   a frame later.

All three fixes are in `Engine::UpdateVRControllerInput(float
timeElapsed)` and the `Run()` XR frame loop in `Engine.cpp` — read the
doc comment directly above `UpdateVRControllerInput()` for the full
mapping table and reasoning; it's kept up to date in-code.

## Open issue — NOT fixed, needs its own investigation

Diagnosed via the user's own testing (closing one eye at a time), not yet
root-caused in code:

- **Stereo HUD double vision**: each eye currently draws an independently
  *centered* copy of the 2D HUD/crosshair (see `RenderOverlaysVR()`/
  `PostRenderVR()` in `RenderCanvas.cpp`, added last session). Centered-
  per-eye only fuses into one image if both eyes' half-viewports map
  "center" to the same real-world gaze direction — that's not true here
  because the real per-eye OpenXR frustums are asymmetric (`angleLeft` !=
  `angleRight` etc., pulled from real tracked FOV in `DrawSceneVR()`).
  The 2D HUD draw path doesn't account for that asymmetry at all, so the
  two centered copies don't converge — hence double vision on the
  crosshair/text specifically (world geometry, which *does* go through
  the real asymmetric-frustum 3D projection, doesn't have this problem).
- **UI outside the headset's FOV**: same root cause from a different
  angle — health/ammo/etc. are still laid out for a full desktop-sized
  screen split in half, not repositioned for a much narrower per-eye
  comfortable viewing cone.
- **World geometry warps as you look around**: genuinely unexplained.
  Could be a real bug in the per-eye pose/FOV composition math in
  `Engine.cpp`'s `Run()` XR frame loop or `RenderScene.cpp`'s
  `DrawSceneVR()` (both from last session, not touched today), or could
  be an inherent visual side effect of a very wide per-eye rectilinear
  FOV (a real, if unusual, characteristic of naive rectilinear projection
  at wide angles — not necessarily a bug). **Do not guess-fix this** —
  it needs actual diagnostic data first (e.g. log the real per-eye
  `angleLeft/Right/Up/Down` values once per session to sanity-check
  their magnitude, or get a raw in-headset screenshot/video if that's
  ever feasible) before attempting a fix.

This is a separate, more involved rendering problem from anything touched
today. Recommend treating it as its own investigation, not a quick
follow-on patch.

## Also worth investigating (lower priority, found as a side effect)

- The `UObject::SetBool()` type-confusion bug (root cause #1 above) is
  generic, not VR-specific. If keyboard/mouse fire has ever felt flaky in
  this engine (there was an earlier, still-unconfirmed suspicion of a
  mouse-fire-not-registering issue, previously guessed to be a
  window-focus artifact), this bug is a more concrete suspect worth
  checking first. A real fix would likely be making `UObject::SetBool()`
  check the actual resolved property type (or type of the specific
  property, e.g. via `dynamic_cast` or a type tag) rather than blindly
  casting — out of scope for a quick fix since it'd need auditing every
  existing caller.
